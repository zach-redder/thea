# thea-brain

PostgreSQL + pgvector data layer for thea. Schema, migrations, and the direct-access repository layer used by thea-heart.

## Overview

thea-brain owns all of thea's persistent data: structured facts about Zach (`identity`, `wardrobe`, `environment`), system configuration and behavior (`thea`), episodic memory (`thea.memories`), and short-term session state (Redis). It's the one repo every other data-touching decision in the system ultimately depends on.

Migrations are **generated, not hand-written** — `generate_migrations.py` builds them directly from the live thea_DB Google Sheet (`schema_registry`/`table_registry`/`column_registry` plus each table's own tab), so the schema in code can never silently drift from what's documented as the schema.

## Role in the thea system

- **thea-heart connects directly** to this database (SQLAlchemy) rather than through HTTP. Decision made explicitly during planning: the context builder issues several queries per conversational turn, and that's latency-sensitive for a voice assistant expected to respond in real time.
- **thea-body** (dashboard) should not get direct DB credentials — it's meant to go through a thin read-only HTTP API layered on top of this repo. Not built yet.
- **thea-muscles** and **thea-senses** don't touch this database at all — they publish events to thea-heart, which owns all reads/writes.
- **Embeddings are generated by thea-heart**, using Voyage AI (Anthropic's recommended embeddings provider — Claude has no embedding model of its own). This repo only stores and searches vectors; it never calls an embeddings API itself.

## Tech stack

- **PostgreSQL 16+** with the **pgvector** extension
- **SQLAlchemy 2.0** (Core, via raw `text()` queries — no heavy ORM mapping layer)
- **psycopg3**
- **Redis** — session/short-term state, separate from `thea.memories`' long-term recall
- **Alembic** — planned for future schema versioning once migrations stabilize beyond the initial generated set

## Structure

```
thea-brain/
├── generate_migrations.py      # builds migrations/*.sql from the live Google Sheet
├── migrations/
│   ├── 0001_extensions_and_public.sql
│   ├── 0002_thea_schema.sql
│   ├── 0003_identity_schema.sql
│   ├── 0004_wardrobe_schema.sql
│   └── 0005_environment_schema.sql
├── app/
│   ├── db.py                   # direct connection layer, used by thea-heart
│   ├── session_store.py        # Redis-backed session state
│   └── repositories/
│       ├── memory_repo.py            # pgvector similarity search over thea.memories
│       └── profile_context_repo.py   # single-row identity.profile / identity.context
├── requirements.txt
└── .env.example
```

## Setup

```
cp .env.example .env   # fill in thea_DATABASE_URL, thea_REDIS_URL
psql $thea_DATABASE_URL -f migrations/0001_extensions_and_public.sql
psql $thea_DATABASE_URL -f migrations/0002_thea_schema.sql
psql $thea_DATABASE_URL -f migrations/0003_identity_schema.sql
psql $thea_DATABASE_URL -f migrations/0004_wardrobe_schema.sql
psql $thea_DATABASE_URL -f migrations/0005_environment_schema.sql
```

## Status

**Partially implemented** — the only repo with real code so far. Migrations, connection layer, session store, and two representative repositories exist. Remaining repositories (goals, relationships, projects, wardrobe items, etc.) follow the same pattern as `profile_context_repo.py` and should be added as thea-heart's context builder needs them, rather than pre-built speculatively.

### Known open items
1. `thea.memories` isn't in the live Google Sheet yet — it exists in migrations via a flagged fallback in `generate_migrations.py`. Sync the sheet, then remove the fallback.
2. Three sheet-side type bugs are patched via `TYPE_OVERRIDES` in the generator (`config.name`, `config.temperature`, `config.do_not_disturb_start`/`end`). Fix the sheet, then remove the overrides.
3. `schema_registry.environment` has a trailing space in the live sheet data — stripped defensively in the generator, worth fixing at the source.
